# Ревью правки COCL

Проект — ~40 JS-модулей с общим глобальным пространством имён, и почти все прошлые баги —
это следы неаккуратной замены: старая функция осталась и перекрыла новую,
поле потерялось при сохранении, обработчик повесили на элемент, который потом
пересоздаётся. Ревью нужно, чтобы ловить именно это до того, как код попадёт
к операторам на линии.

## 1. Механические проверки (скрипт)

```bash
python3 .claude/skills/cocl-review/scripts/review_checks.py --base origin/main
```

Скрипт сравнивает рабочее дерево с базой и находит:
- удалённые функции, на которые остались ссылки (во всех модулях js/, onclick в HTML);
- функции верхнего уровня, объявленные дважды (вторая молча перекрывает первую);
- новые функции, которые нигде не вызываются;
- рост числа `classList.add/remove('active')` на модалках и `console.log`;
- изменённый `STORAGE_KEYS`;
- удалённые из index.html id, которые ещё ищет JS;
- сохранение расписания и нормализация параметра без `timeWindows`
  (`saveScheduleWeekOverride`, `setRowTemplateFrom`, `normalizeElectronicFrequency`);
- hex-цвета в CSS вместо переменных;
- смену переводов строк CRLF → LF (файлы проекта в CRLF);
- порядок подключения модулей (`check_load_order.js`): код, выполняемый при
  загрузке, не должен требовать функций из модулей, подключённых позже, и
  одноимённых функций в разных модулях быть не должно.

Каждое замечание — либо исправить, либо объяснить в ответе, почему это не проблема.

## 2. Смысловое ревью

Скрипт не понимает смысла. Для крупной правки (новая функциональность, правка
нескольких вкладок, изменение формата данных) лучше запустить отдельного агента,
который не видел, как писался код, и дать ему diff (`git diff origin/main`) и этот
чек-лист — свежий взгляд замечает то, что автор считает очевидным. Для мелкой
правки пройди чек-лист сам.

Чек-лист:
1. **Данные пользователей.** Старые записи в localStorage читаются новой версией?
   Новое поле имеет значение по умолчанию при чтении (нормализация), а не только
   в форме? Есть ли миграция, если меняется формат?
2. **Все места вызова.** Если поменялась сигнатура или поведение функции — найди
   все вызовы (`grep -rn "имя(" js index.html`) и проверь каждый.
3. **События.** Элемент создаётся динамически или модалка пересоздаётся — нужно
   делегирование. Нет ли двойной привязки обработчика при повторном открытии?
4. **Модалки.** Открытие поверх другой — через `openModal`, иначе ломается стек.
5. **SMD vs PMD/FMD.** Логика `nodePart` (Maker/Packer) срабатывает только для SMD?
6. **Типы контроля.** Учтены все три: `fixed` (с точками и без), `variable`,
   `interval`? Electronic и механика обработаны?
7. **Смены и бригады.** Не перепутаны смена (день/ночь) и бригада (A/B/C/D)?
8. **Мёртвый код.** Удалены заменённые функции, HTML, CSS-правила, обработчики.
9. **Тексты интерфейса** — по-русски, в стиле соседних элементов.
10. **Документация.** Правка меняет поведение, описанное в PROJECT_SUMMARY.txt? Это
    пойдёт в `cocl-session-close`, но отметь сразу.

## 3. После ревью

Исправь найденное, затем прогони `cocl-smoke-test`. В ответе пользователю — коротко:
что проверено и что исправлено по итогам ревью, без пересказа всего чек-листа.
