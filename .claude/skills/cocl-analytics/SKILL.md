# Аналитика COCL

Цель — не «отчёт с графиками», а короткий список: **что не так → почему → что сделать → кто решает**.
Читатель — аналитик участка или начальник смены. Успех: прочитал и знает, что делать на
следующей смене, без уточняющих вопросов. Находка без действия — выкинуть.

## С чего начинать всегда

1. **Какой результат главный.** Спроси один раз, если неясно:

   | Запрос | Главный результат | На что влияем |
   |---|---|---|
   | Разбор линии / участка | стандарты держатся в норме | правка стандарта, ремонт, обучение |
   | Выполнение расписания CL | проверки делаются в свои смены | расписание, загрузка смены, напоминания |
   | TOP Losses | потеря не повторяется | какой стандарт/узел закрыть проверкой |
   | Переходы (COCL) | после смены сорта всё в норме | триггеры, точки брендов, порядок перехода |

2. **Период и линии.** По умолчанию — последние 30 дней, все линии с данными.
3. **Хватает ли данных** (ниже). Нет — так и пиши, не додумывай.

## Данные

- **Бэкап** `checklist_backup_*.json` (экспорт из Настроек): `history`, `standards`, `shifts`,
  `workshops`, `topLosses`, `operators`. Свежий файл попроси у пользователя — тот, что в
  репозитории, тестовый (много пробных записей).
- Запись `history`: `mode` — `cl` (Чек-лист CL, мех.), `electronic` (E-Param), `toploss`,
  пусто — COCL (переходы, поле `type`). `line`, `shift` (буква A/B/C/D), `date` (у CL),
  `timestamp`, `items[]`: `standardId`, `oplNumber`/`standardNumber`, `title`/`checkPoint`,
  `machine`, `node`, `nodePart`, `status` (`OK` / `FAIL` / иначе не проверено), `answer`,
  `value(s)`, `comment`, `deviation`.
- Смена записи без `date`: день 09:00–21:00, ночь 21:00–09:00; ночь после полуночи — к
  предыдущей дате (как `histShift` в `js/views/history/history-data.js`).
- **Пропущенные смены и % выполнения расписания** зависят от версий шаблона расписания
  (`getRowForWeek`) — их считает приложение (Дашборд, История → Excel). Скрипт их не
  пересчитывает: бери из приложения или из Excel Истории, не изобретай свою формулу.

## Скрипт

```bash
node .claude/skills/cocl-analytics/scripts/analyze_backup.js --backup <файл.json> [--days 30] [--to 2026-10-23] [--line SD12] [--json <scratchpad>/a.json]
```

Без `--backup` берёт самый свежий `checklist_backup_*.json` в корне. Печатает сводку в
Markdown: итоги по видам проверок, линии, повторяющиеся отклонения (серии подряд),
стандарты/машины с долей «Не ОК», сравнение смен A/B/C/D, TOP Losses, переходы, и
блок «мало данных». `--json` — то же в JSON для своих расчётов.
Цифры для отчёта бери из вывода скрипта, не пересчитывай в голове.

## Как думать

- **Отклонения, а не среднее.** «92% в норме по линии» прячет стандарт, который не в норме
  каждую смену. Спускайся: линия → машина → стандарт → точка; смена A/B/C/D; бренд.
- **Повтор важнее количества.** 3 «Не ОК» подряд у одного стандарта — сигнал (так же считает
  «Требует внимания» на Дашборде: `dashFailStreak`). 3 разных стандарта по разу — шум.
- **Не рубить на малых данных.** Порог для вывода «системно»: ≥ 5 проверок стандарта за
  период; сравнение смен — ≥ 10 проверок у каждой. Меньше — «наблюдать», а не «менять».
- **Каждое значение — из данных.** Нет поля — «этих данных нет». Не придумывать нормы,
  причины и «типичные» значения.
- **Различай, что сломалось:**
  - одна точка всегда за одной границей нормы, у всех смен → **оборудование** (заявка на
    ремонт / наладку). Не советовать «пересмотреть норму»: стандарт пересматривается только
    в случаях, которые определил пользователь (уточнить у него и записать сюда);
  - отклонения только у одной смены → **обучение / способ замера** (OPL, показ на месте);
  - отклонения после перехода на конкретный бренд → **точки бренда** в стандарте;
  - стандарт не проверяют, хотя в расписании → **расписание или загрузка смены**.
- **Люди.** Сравнение смен — про процесс и обучение, не про виноватых. Фамилии операторов в
  выводы не выносить; решения по людям — только человек.

## Формат отчёта (планёрка)

```markdown
# Разбор CL: <линии>, <период>
## Главное (3–5 строк: что сделать на этой неделе)
## Повторяющиеся отклонения — стандарт, серия, значения, предлагаемое действие
## Где проседает — машины / смены / бренды (только при достаточных данных)
## TOP Losses — потери с проверками «Не ОК», какой стандарт закрывает
## Выполнение расписания — из Дашборда/Истории (не из скрипта)
## Мало данных — что не выводим и что дособрать
## Решает человек — правка стандарта, ремонт, обучение, изменение расписания
```

У каждого пункта «действие»: кто (аналитик участка / мастер / смена), что, к какому сроку.
Короткие фразы, термины проекта: «смена A», «стандарт OPL-…», «аналитик участка»
(не «технолог», не «бригада»).

Отчёт для других людей — оформи артефактом/файлом; для пользователя в чате — коротко.

## Виджеты Дашборда и Истории

При проектировании нового показателя (вместе с `dataviz`):
- показатель отвечает на вопрос «что делать», иначе не нужен; рядом — сравнение с прошлым
  периодом и переход к деталям (стандарт / линия / смена);
- «Требует внимания» — конкретные пункты с действием, отсортированные по серьёзности:
  повтор подряд > пропущенная смена. Значение «у границы нормы» не показывать: в норме —
  значит в цели, это не сигнал;
- пороги «мало данных» показывать в интерфейсе («мало проверок»), а не прятать;
- цвета — смысловые цвета проекта (`CLAUDE.md`, п. 8): красный — отклонения,
  амбер — TOP Losses, зелёный — ОК.

## Чего не делать

- Не менять данные пользователя: только чтение бэкапа.
- Не выдавать список цифр без выводов и выводы без цифр.
- Не советовать «убрать стандарт» или «поменять норму» по 1–2 проверкам.
