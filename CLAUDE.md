# COCL — инструкции для Claude

Производственный веб-инструмент для табачной фабрики: регулярные проверки
механических стандартов (OPL) и электронных параметров оборудования CL (CenterLine),
проверки смены сорта (COCL), TOP Losses, расписание проверок для аналитиков.
Терминология: стандартами и расписанием управляют «аналитики участков» — слово «технолог» не используем (UI, комментарии, документы).

Начало сессии: `Handoff.md` (где остановились, что дальше). Где что в коде —
`PROJECT_MAP.md` (JS-модули и их функции со строками, CSS-файлы, ключи localStorage).
Читай только нужный модуль, а не весь код — так экономятся лимиты.
Связи между модулями («кто вызывает», «что затронет правка») — граф graphify:
`graphify query "<вопрос>"` / `graphify explain "<узел>"` по `graphify-out/graph.json`.
`PROJECT_SUMMARY.txt` (1800+ строк) — только в исключительных случаях, когда карты,
графа и `Handoff.md` не хватает (формат данных, история решений); и то — один нужный
раздел, не целиком. Обновлять его при закрытии сессии — как прежде.
Этот файл — короткая выжимка того, что нужно держать в голове всегда.

Язык общения с пользователем — русский. Тексты интерфейса — русские.

## Архитектура

- Чистый HTML + CSS + JS, без фреймворков и сборки. Работает через `file://`
  (двойной клик по `index.html`), сервера нет. Данные — только в `localStorage`.
- SPA: один `index.html`, вкладки — `div.tab#tab-<name>`, переключение —
  `switchTab()` в `js/router.js` (hash-роутинг). Дефолтная вкладка — `electronic`
  (Чек-лист CL), не `check`.
- JS разбит на ~40 модулей в `js/` (с сессии 7): `core/` (утилиты, состояние, даты,
  модалки) → `data/` (доступ к localStorage) → `components/` (общие окна) → `io/`
  (Excel) → `views/<вкладка>/` → `js/app.js` (запуск, последним). Это обычные
  `<script>` в `index.html` с **общим глобальным пространством имён** — не ES-модули
  (`file://` не даёт import). Карта — `PROJECT_MAP.md`.
- **Порядок подключения важен.** Код, который выполняется при загрузке
  (`addEventListener('click', f)`, вызовы на верхнем уровне), не может ссылаться на
  функцию из модуля, подключённого позже: в `addEventListener` передавай `() => f()`
  или клади функцию в более ранний модуль. Проверка:
  `node .claude/skills/cocl-review/scripts/check_load_order.js`.
- Новый код — в модуль своей вкладки; общее — в `core/` или `data/`. Новый файл —
  добавить `<script>` в `index.html` в нужное место. Модуль больше ~1000 строк — делить.
- CSS: `style.css` (точка входа) → `css/base.css` (переменные темы),
  `css/layout.css`, затем `css/components/*` и `css/views/*` (по вкладкам) — список и
  порядок @import в `style.css`. **Порядок @import = порядок каскада, не менять.**
  Новые правила — в конец файла своей вкладки. Тема light/dark через CSS-переменные.
- Библиотеки: только `js/exceljs.min.js` и `js/jszip.min.js` (локально). Новые — только по согласованию.
- Фото: `photos/<line>/<Maker|Packer>/<file>`, в стандарте хранится только имя
  файла, путь собирает `getPhotoPath()`. Папки `photos/` в репозитории нет — у
  каждого пользователя своя копия, отсутствующие фото это норма.

## Предметная область (кратко)

- Иерархия: Цех (SMD/PMD/FMD) → Участок → Блок (LST 1/2, у PMD нет) → Линия.
  `DEFAULT_WORKSHOPS` в `js/core/state.js`; доступ через `getWorkshops`, `getBlockForLine`,
  `getAllLinesWithContext`, `getWorkshopIdForLine`.
- Часть линии Maker/Packer (`nodePart`) — только для SMD; в PMD/FMD поле скрыто и
  не валидируется.
- OPL № уникален в пределах линия + машина.
- Типы контроля: `fixed` / `variable` (92 ± 5) / `interval` (5 до 8). Legacy-типы
  мигрирует `migrateControlType` — не ломать.
- Смены: день 09:00–21:00, ночь 21:00–09:00. A/B/C/D — буквы смен (в интерфейсе везде «смена», слово «бригада» не используем).
- Время проверки считается само (`autoTimeWindows(work, schedule)` в `js/data/schedule.js`):
  Run/Stop — первый час смены (09:00–10:00 день, 21:00–22:00 ночь) по отмеченным сменам;
  CIL — без окна, чип времени не показывается. Вручную не задаётся; хранимые `frequency.timeWindows`
  не читать, но не терять при сохранении. Поля `timeFrom/timeTo` и `number` — только
  для совместимости.
- Легенда (`js/components/legend.js`) — только в Чек-листе CL и Расписании CL; в Стандартах CL
  её нет. Горячие клавиши — `js/components/hotkeys.js`.
- Расписание: шаблон строки хранится версиями `frequency.templates` (с какой недели
  действует) + разовые правки недели `cl_schedule_weeks_v1`. Неделю всегда считать
  через `getRowForWeek`, не читать `frequency.schedule` напрямую. Прошлое не меняется.
- Создание/правка стандарта — страница `#tab-standard-view` (`svFullState`),
  E-Param — страница `#tab-eparam-edit` (`epPageState`); модалок форм больше нет.
- Тип ↔ значение: fixed не принимает `N ± M` и `N до M`, variable — только `N ± M`,
  interval — только `N до M` (`classifyNormValue`, `normTypeError`). Точка-метка словами
  («метки совпадают», `isNormMark` — начинается со слова) допустима в любом типе: в проверках
  (быстрая, TOP Losses, CL при переходах) это кнопки ОК / Не ОК. Неизменённые старые значения
  не блокируют сохранение. Валидация нового стандарта — минимум 28 смен (`VALIDATION_SHIFTS`); по истечении срока
  стандарт сам становится обычным (статус `ended`), в расписании не продлевается — только
  вручную «+28 смен».
- Работа: Run → Stop → CIL (`WORK_CYCLE`). Окна проверки: 09:00–10:00 / 21:00–22:00, CIL —
  без окна и никогда не «просрочен».
- В интерфейсе «CL относится к» (не «Применять к»). Стандарт открывается по адресу
  `#standard/<id>` (`openStandardFromHash`); недавно открытые — `cl_recent_standards`.
- Excel стандартов и E-Param — без макросов: формулы + выпадающие списки, скрытый лист
  «Списки» (`js/io/standards-io.js`, `editor-elec.js`). Импорт — по номеру колонки, понимает
  старый формат, проверяет «тип ↔ значение».
- Бэкап берёт все ключи `STORAGE_KEYS` (`collectBackup` / `applyBackup`) — новый ключ
  добавлять только в `STORAGE_KEYS`. ZIP с фото — Настройки → Данные.
- Аналитика: доля «N из M» и «мало проверок» вместо голых чисел; «у границы нормы» не
  показываем (в норме — значит в цели); «пересмотреть норму» не советовать.
  «Открытые / не устранённые отклонения» не показываем: об устранении на месте (Machine
  Journal) данных нет — только отклонения за период.
- Дашборд: показатели, таблица «участок → линия → Maker/Packer → машина», динамика по
  неделям, смены A–D; паспорт линии — оборудование плитками. Режима «Сейчас» нет.
  История: шапка в одну строку + «Фильтры» (смена, тип), лента по сменам, календарь
  «7 дней / Месяц» (`histCalHtml`); фильтров цеха и машины нет.
- Визуальные правки — по макетам на полотне Design в claude.ai «точь в точь»; перед ответом
  сверять скриншотом headless-браузера.
- Существенное изменение (одно правило для листа изменений линии, истории стандарта и
  ознакомления — `CL_SHEET_KEYS`, `stdAckIsMajor`): основная информация, описания, инструмент,
  время на проверку, точки/бренды, фото, создание/удаление/деактивация/восстановление.
  «CL относится к», «всегда в Change Over», триггеры, Top Losses — не существенно (в истории
  стандарта серой строкой, в лист линии не попадают). Полная история — на странице стандарта.
- Названия блоков стандарта везде (проверки, просмотр, Excel) — как на странице стандарта:
  «Описание», «Описание контроля» (не «Как проверять»), «Цель (зачем мы это делаем?)»,
  «Знаю почему (почему создан стандарт?)»; у E-Param — «Что считается «ОК»».
- Проверка в «CL при переходах» и TOP Losses — одно окно «список слева — стандарт справа»
  (`js/components/check-run.js` + `css/components/check-run.css`): инструмент, время на
  проверку, точки, «Описание контроля», комментарий в окне (обязателен при отклонении), фото,
  «Весь стандарт». Окна комментария больше нет.
- Комментарии к стандарту / E-Param — `cl_std_comments_v1` (`js/data/comments.js`),
  ознакомление — `cl_std_ack_v1` (`js/data/ack.js`; редакция = 1 + число существенных
  изменений; повторно — после существенного изменения; метка «Изм.» в Чек-листе CL),
  колокольчик — `js/components/notify.js`. Автор везде «—» до автологина.
- ChangeOver: стандарт показывается, только если точки брендов различаются
  (`brandBlocksDiffer`) или `forceInChangeOver === true`.

## Правила работы с кодом

1. **Хранилище.** Ключи — в `STORAGE_KEYS`. Менять ключ или формат данных только с
   миграцией: у пользователей на заводе реальные данные в `localStorage`, потерять
   их нельзя. При сохранении расписания не терять `frequency.timeWindows`.
2. **Модалки** — только через `openModal` / `closeModal` (стек `modalStack`),
   никаких ручных `classList.add('active')`.
3. **События.** Статичные id — `addEventListener` напрямую; динамически созданные
   элементы и пересоздаваемые модалки — только делегирование.
4. **Мёртвый код удалять сразу** при замене: старую функцию, неиспользуемый HTML,
   CSS-правила, обработчики, глобальные переменные. Проверка — поиск по имени.
5. **Не переименовывать** существующие id/классы и не удалять функции, не проверив
   все вызовы (включая `router.js` и `onclick` в `index.html`).
6. **Стиль:** отступ 2 пробела, camelCase, разделители-комментарии вида
   `/* === НАЗВАНИЕ === */`, цвета только через CSS-переменные, иконки только SVG
   (Feather) с явными width/height.
7. **Переводы строк.** JS, `index.html`, CSS и `PROJECT_SUMMARY.txt` — в CRLF.
   Правь точечно через Edit; не переписывай файл целиком через Write или скриптом с
   LF — иначе diff будет на весь файл и ревью станет невозможным.
8. **Цвета смысла:** циан — активное/действия/ChangeOver/дневные окна; фиолетовый —
   просмотр/CL в ТО/ночные окна; изумрудный — CL в Конвертацию; зелёный — ОК/RUN;
   красный — отклонения; амбер — Top Losses/fixed-галочка/STOP.

## Как проверять правку

1. `node --check` изменённых JS-файлов и `check_load_order.js` (см. выше).
2. `node --test tests/logic.test.js` — автотесты логики без браузера (нормы и типы
   контроля, точки-метки, смены, недели, расписание, валидация). Правишь эту логику —
   добавь тест на новый случай.
3. Скилл `cocl-smoke-test` — headless-браузер обходит все вкладки и формы и ловит
   ошибки JS. Не говорить «готово», пока он не зелёный.
4. Для крупной правки — скилл `cocl-review` (проверка по правилам выше).
5. Визуальные правки — посмотреть скриншоты из смоук-теста.

## Как отдавать результат пользователю

- Claude правит файлы сам и коммитит в ветку, а в ответе кратко пишет, что и где
  изменено (файл, функция, суть). Формат «найди → замени» — только если
  пользователь вносит правку руками или просит именно так.
- Изменения — через ветку и pull request в `main`, не прямой push в `main`, пока
  пользователь не скажет иначе.
- В конце рабочей сессии — скилл `cocl-session-close`: обновить
  `PROJECT_SUMMARY.txt` и `ROADMAP.txt` по фактическим изменениям.

## Какой скилл для какой задачи

| Задача | Скилл |
| --- | --- |
| После любой правки кода | `cocl-smoke-test` |
| Перед коммитом / PR крупной правки | `cocl-review` (+ общий `engineering:code-review`) |
| Конец рабочей сессии | `cocl-session-close` |
| Баг с непонятной причиной | `diagnosing-bugs` (петля воспроизведения — headless-браузер из смоук-теста), затем `cocl-smoke-test` |
| Новый экран или переделка вида | `frontend-design` — но в рамках существующей палитры и CSS-переменных проекта, не новый стиль |
| Оценка вида после правки | `design:design-critique` по скриншотам из смоук-теста |
| Новая функция с неясными требованиями (до кода) | `grilling` — вопросы раундами с рекомендуемым ответом |
| Разбор проверок, отчёт для планёрки, «где проблемы» | `cocl-analytics` |
| Виджеты дашборда, графики | `dataviz` (+ правила показателей из `cocl-analytics`) |
| Экспорт / импорт XLSX | `xlsx` — проверить, что файл открывается и листы правильные |
| Сводка сделанного для планёрки | `engineering:standup` по коммитам |
| Новый или улучшенный проектный скилл | `skill-creator` |
