# COCL — инструкции для Claude

Производственный веб-инструмент для табачной фабрики: регулярные проверки
механических стандартов (OPL) и электронных параметров оборудования CL (CenterLine),
проверки смены сорта (COCL), TOP Losses, расписание проверок для технологов.

Полное описание — `PROJECT_SUMMARY.txt`: структура данных, все вкладки, функции,
история сессий, что осталось. Читай нужный раздел перед правкой незнакомой области.
Этот файл — короткая выжимка того, что нужно держать в голове всегда.

Язык общения с пользователем — русский. Тексты интерфейса — русские.

## Архитектура

- Чистый HTML + CSS + JS, без фреймворков и сборки. Работает через `file://`
  (двойной клик по `index.html`), сервера нет. Данные — только в `localStorage`.
- SPA: один `index.html`, вкладки — `div.tab#tab-<name>`, переключение —
  `switchTab()` в `js/router.js` (hash-роутинг). Дефолтная вкладка — `electronic`
  (Чек-лист CL), не `check`.
- Вся логика в `app.js` (~20 000 строк, ~470 функций). **Не разбивать на модули
  без согласования с пользователем.**
- CSS: `style.css` (точка входа) → `css/base.css` (переменные темы),
  `css/layout.css`, `css/components.css`. Тема light/dark через CSS-переменные.
- Библиотеки: только `js/exceljs.min.js` (локально). Новые — только по согласованию.
- Фото: `photos/<line>/<Maker|Packer>/<file>`, в стандарте хранится только имя
  файла, путь собирает `getPhotoPath()`. Папки `photos/` в репозитории нет — у
  каждого пользователя своя копия, отсутствующие фото это норма.

## Предметная область (кратко)

- Иерархия: Цех (SMD/PMD/FMD) → Участок → Блок (LST 1/2, у PMD нет) → Линия.
  `DEFAULT_WORKSHOPS` в `app.js`; доступ через `getWorkshops`, `getBlockForLine`,
  `getAllLinesWithContext`, `getWorkshopIdForLine`.
- Часть линии Maker/Packer (`nodePart`) — только для SMD; в PMD/FMD поле скрыто и
  не валидируется.
- OPL № уникален в пределах линия + машина.
- Типы контроля: `fixed` / `variable` (92 ± 5) / `interval` (5 до 8). Legacy-типы
  мигрирует `migrateControlType` — не ломать.
- Смены: день 09:00–21:00, ночь 21:00–09:00. A/B/C/D — **бригады**, не смены.
- Время проверки — в `frequency.timeWindows` (задаётся в Расписании CL), поля
  `timeFrom/timeTo` и `number` оставлены только для совместимости.
- ChangeOver: стандарт показывается, только если точки брендов различаются
  (`brandBlocksDiffer`) или `forceInChangeOver === true`.

## Правила работы с кодом

1. **Хранилище.** Ключи — в `STORAGE_KEYS`. Менять ключ или формат данных только с
   миграцией: у пользователей на заводе реальные данные в `localStorage`, потерять
   их нельзя. При сохранении расписания не терять `frequency.timeWindows`.
2. **Модалки** — только через `openModal` / `closeModal` (стек `modalStack`),
   никаких ручных `classList.add('active')`.
3. **События.** Статичные id — `addEventListener` напрямую; динамически созданные
   элементы и пересоздаваемые модалки — только делегирование.
4. **Мёртвый код удалять сразу** при замене: старую функцию, неиспользуемый HTML,
   CSS-правила, обработчики, глобальные переменные. Проверка — поиск по имени.
5. **Не переименовывать** существующие id/классы и не удалять функции, не проверив
   все вызовы (включая `router.js` и `onclick` в `index.html`).
6. **Стиль:** отступ 2 пробела, camelCase, разделители-комментарии вида
   `/* === НАЗВАНИЕ === */`, цвета только через CSS-переменные, иконки только SVG
   (Feather) с явными width/height.
7. **Переводы строк.** `app.js`, `index.html`, CSS и `PROJECT_SUMMARY.txt` — в CRLF.
   Правь точечно через Edit; не переписывай файл целиком через Write или скриптом с
   LF — иначе diff будет на весь файл и ревью станет невозможным.
8. **Цвета смысла:** циан — активное/действия/ChangeOver/дневные окна; фиолетовый —
   просмотр/CL в ТО/ночные окна; изумрудный — CL в Конвертацию; зелёный — ОК/RUN;
   красный — отклонения; амбер — Top Losses/fixed-галочка/STOP.

## Как проверять правку

1. `node --check app.js` (и `js/router.js`, если трогал).
2. Скилл `cocl-smoke-test` — headless-браузер обходит все вкладки и формы и ловит
   ошибки JS. Не говорить «готово», пока он не зелёный.
3. Для крупной правки — скилл `cocl-review` (проверка по правилам выше).
4. Визуальные правки — посмотреть скриншоты из смоук-теста.

## Как отдавать результат пользователю

- Claude правит файлы сам и коммитит в ветку, а в ответе кратко пишет, что и где
  изменено (файл, функция, суть). Формат «найди → замени» — только если
  пользователь вносит правку руками или просит именно так.
- Изменения — через ветку и pull request в `main`, не прямой push в `main`, пока
  пользователь не скажет иначе.
- В конце рабочей сессии — скилл `cocl-session-close`: обновить
  `PROJECT_SUMMARY.txt` и `ROADMAP.txt` по фактическим изменениям.

## Какой скилл для какой задачи

| Задача | Скилл |
| --- | --- |
| После любой правки кода | `cocl-smoke-test` |
| Перед коммитом / PR крупной правки | `cocl-review` (+ общий `engineering:code-review`) |
| Конец рабочей сессии | `cocl-session-close` |
| Баг с непонятной причиной | `engineering:debug`, затем `cocl-smoke-test` |
| Новый экран или переделка вида | `frontend-design` — но в рамках существующей палитры и CSS-переменных проекта, не новый стиль |
| Оценка вида после правки | `design:design-critique` по скриншотам из смоук-теста |
| Виджеты дашборда, графики | `dataviz` |
| Экспорт / импорт XLSX | `xlsx` — проверить, что файл открывается и листы правильные |
| Сводка сделанного для планёрки | `engineering:standup` по коммитам |
| Новый или улучшенный проектный скилл | `skill-creator` |
